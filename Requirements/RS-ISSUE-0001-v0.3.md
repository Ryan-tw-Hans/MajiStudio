## 1. 已確認目標與範圍

系統是在 Android 手機上拍攝或選取名片影像，使用 OCR 將內容轉為可編輯的聯絡人資訊。辨識模式依使用者選擇分為離線 OCR、雲端 OCR 與 AI 結構化解析。

本版已確認：

1. 離線 OCR 預設可用；雲端 OCR 與 AI 只在使用者主動啟用並同意資料傳送後使用。
2. 相機對焦可用後，開始以最新影格做離線即時 OCR，持續更新未鎖定候選。
3. 使用者點選候選文字後，文字與目前欄位對應會被鎖定，不再受即時 OCR 覆寫；再次點選才讓該項重新掃描。
4. 使用者鎖定文字後，可用欄位名稱下拉選單重新分類，且不應重新辨識文字。
5. 使用者按下完成後，必須保存兩種本機正式資料：原始名片影像，以及已確認的結構化聯絡人資料。
6. 結構化資料由 App 私有 Room / SQLite 管理；原始影像存於 App 私有持久檔案區，並以 SQLite 的資產 metadata 與聯絡人記錄關聯。這不表示影像會放到系統相簿、共享儲存、雲端或其他 App 可讀的位置。
7. 完整原始 OCR 文字、即時預覽影格、裁切或前處理衍生影像仍不作永久保存，除非未來另立需求。

本版不代表 Android App、雲端帳號、API 金鑰、資料庫額外加密、備份規則或正式部署已建立。

## 2. 主要使用流程

1. 使用者開啟相機預覽並將名片放入取景框，也可從裝置選取既有影像。
2. App 顯示對焦與取景提示。當相機對焦可用且可分析時，開始離線即時 OCR。
3. App 僅更新未鎖定的候選文字，並將候選映射到姓名、公司、職稱、電話、電子郵件、網站、地址或未分類欄位。
4. 使用者點選候選文字，將其文字與欄位對應鎖定。
5. 若欄位名稱錯誤，使用者在 Locked 狀態下以欄位名稱下拉選單重新分類；這不會重新執行 OCR。
6. 使用者再次點選 Locked 文字，可讓該項重新加入掃描；其他 Locked 欄位維持不變。
7. 使用者可手動新增、刪除或編輯所有欄位。
8. 使用者可選擇雲端 OCR 或 AI 解析；每次資料離開手機前都必須顯示同意說明與取消選項。
9. 使用者按下完成後，App 先在私有暫存區安全寫入原始輸入影像，再建立聯絡人、欄位及影像 metadata，最後完成影像定稿。
10. 只有影像與結構化資料都進入可讀取的完成狀態後，App 才可顯示「已完成存檔」；中斷或失敗須保留可復原狀態或讓使用者重試，不能顯示假成功。
11. 後續本機查詢可讀取結構化欄位，並在該筆資料詳情中載入相對應的原始名片影像。
12. Android Contacts 匯出是另行、可取消的動作；SQLite 已存檔不等於 Android Contacts 已成功新增。

## 3. 功能需求

| ID | 需求 |
| --- | --- |
| FR-01 | App 必須支援相機預覽拍攝單張名片與相簿選取影像。雙面名片是否納入第一版為待決事項。 |
| FR-02 | App 必須處理影像方向、取景引導、重拍與裁切。影像模糊或文字不足時，必須提供重拍與手動輸入，不得把低可信結果當成已確認值。 |
| FR-03 | 離線 OCR 為初始選項；在飛航模式下，拍攝、即時 OCR、欄位鎖定、手動編輯、完成存檔與本機查詢均須可用。 |
| FR-04 | 相機對焦可用時，App 必須啟動即時 OCR；一次僅可執行一個分析工作，新影格必須取代排隊的舊影格，避免 OCR 工作阻塞預覽。 |
| FR-05 | 硬體未提供可靠對焦狀態或持續無法取得清晰結果時，App 必須顯示對焦提示，並提供手動掃描或拍照後辨識的退路。 |
| FR-06 | OCR 模組必須保留當次暫存的候選文字、位置資訊與版本號，讓晚到的 OCR 結果無法覆寫新一代結果或 Locked 欄位。 |
| FR-07 | 候選文字必須具有 Live、Locked、RescanRequested 狀態。只有 Live 項目可由新的 OCR 結果更新。 |
| FR-08 | 使用者點選 Live 候選後，App 必須鎖定其文字值與目前欄位。Locked 項目不得被背景 OCR、自動欄位解析或雲端結果覆寫。 |
| FR-09 | 使用者再次點選 Locked 項目後，App 必須只解除該項目並要求重新掃描；在取得新有效候選前保留舊值供使用者保留、修改或取消。 |
| FR-10 | Locked 項目必須提供欄位名稱下拉選單，可選姓名、公司、職稱、電話、電子郵件、網站、地址、備註或未分類。重新分類不得重新執行 OCR。 |
| FR-11 | 若目標欄位已有 Locked 值，重新分類時必須由使用者選擇保留既有值、加入另一筆值或取代；不得靜默覆寫。 |
| FR-12 | 使用者必須能手動新增、修改或刪除任何欄位；OCR 成功不是完成存檔的必要條件。 |
| FR-13 | 雲端 OCR 與 AI 必須由使用者主動觸發。每次傳送前顯示服務名稱、傳送資料類型、隱私說明與取消選項；不得自動改送其他供應商。 |
| FR-14 | AI 解析預設傳送 OCR 文字；若要傳送名片影像，必須取得另一層影像傳送同意。 |
| FR-15 | 完成操作必須以 Room 交易寫入聯絡人主資料、多筆電話、電子郵件、網址、地址等子資料，以及原始影像的 metadata。交易失敗時不得留下可被一般查詢看見的半筆完成資料。 |
| FR-16 | App 必須保存使用者送入流程的原始名片影像：相機來源為完成拍攝的原始輸出，選取來源則複製為 App 私有副本；不可只保存可能失效的外部 URI。OCR 用的低解析影格、裁切與旋轉衍生品不是本需求的永久資產。 |
| FR-17 | 原始影像必須存放在 App 私有持久檔案區，使用不可預測的資產識別名稱；SQLite 僅保存受控的相對路徑、雜湊、MIME 類型、大小、尺寸、來源與狀態。不得以公開共享儲存或任意絕對路徑保存。 |
| FR-18 | 因影像檔案與 SQLite 不具同一個原子交易，App 必須使用 `PendingFinalize`、`Ready`、`Failed` 等狀態及啟動復原程序，確保一般查詢只顯示影像和結構化資料皆完整的記錄。 |
| FR-19 | SQLite 中的完成聯絡人與影像資產 metadata 是後續查詢系統的正式索引來源；查詢須經 Repository／DAO 與受控影像服務，不得直接暴露資料庫檔、任意檔案路徑或完整 dump。 |
| FR-20 | 第一版可使用 Android 新增聯絡人 Intent 開啟系統聯絡人編輯畫面；App 必須分別追蹤本機保存結果與 Android Contacts 匯出結果。 |

## 4. 即時 OCR 與欄位鎖定狀態

| 狀態 | 進入條件 | 可更新範圍 | 離開條件 |
| --- | --- | --- | --- |
| Focusing | 相機啟動、焦點不穩或名片未在取景框 | 不覆寫任何欄位 | 對焦可用、使用者手動掃描或選取既有影像 |
| Live | 分析可執行 | 僅未鎖定候選可由最新 OCR 結果更新 | 使用者鎖定、停止掃描或離開取景 |
| Locked | 使用者點選候選文字 | 值與欄位名稱固定；仍可手動編輯或重新分類 | 使用者再次點選該項 |
| RescanRequested | 使用者再次點選 Locked 項目 | 只允許此項等待新候選；其他 Locked 項目不變 | 新候選出現、使用者取消或手動輸入 |
| Saving | 使用者確認完成 | 不再接受本次即時 OCR 更新；持續呈現保存進度 | 影像與 SQLite 都 Ready，或顯示可復原錯誤 |
| Completed | 影像與資料庫已完成定稿 | 可由查詢模組讀取；不再被本次掃描更新 | 由未來查詢／編輯需求處理 |

即時 OCR 的節流、候選穩定判定與相機硬體差異，必須以目標裝置測試決定；不得承諾每個影格、每台手機或每種名片都能即時更新。

## 5. 完成後的本機資料範圍

| 資料 | 完成後是否保存 | 保存位置與用途 |
| --- | --- | --- |
| 原始名片影像 | 是 | App 私有持久檔案區；由 SQLite 的 `card_image_assets` 記錄關聯、驗證及查詢。 |
| 已確認的姓名、公司、職稱、備註 | 是 | App 私有 Room / SQLite；供本機聯絡人查詢。 |
| 已確認的電話、電子郵件、網址、地址 | 是，可多筆 | App 私有 Room / SQLite；保留類型、順序與來源。 |
| 影像 SHA-256、MIME、大小、尺寸、來源及 Ready 狀態 | 是 | App 私有 Room / SQLite；確認影像完整、建立查詢索引與復原判斷。 |
| 資料來源模式與完成時間 | 是 | App 私有 Room / SQLite；追溯資料由手動、OCR 或 AI 建立。 |
| Android Contacts 匯出狀態 | 是 | App 私有 Room / SQLite；區分本機已存檔與系統聯絡人已建立。 |
| 即時影格、未鎖定候選、完整原始 OCR 全文 | 否，預設 | 只留在當次記憶體或暫存；不可因保存影像而一併長期保存。 |
| GPT、Gemini、雲端 OCR 的長期 API 金鑰或 ChatGPT 登入憑證 | 否 | 不得存入 App、SQLite、影像 metadata、日誌或錯誤回報。 |

## 6. 非功能需求與驗收方向

| ID | 需求／來源 | 驗證方式與通過標準 | 責任 |
| --- | --- | --- | --- |
| NFR-01 | 離線優先與隱私 | 飛航模式下可完成即時 OCR、鎖定、手動編輯、影像與 SQLite 保存及查詢；未同意時封包不得出現名片資料。 | 測試 |
| NFR-02 | 即時互動穩定性 | OCR 分析延遲或新影格到達時，預覽不被阻塞；Locked 值不變；RescanRequested 只影響指定項目。 | 軟體／測試 |
| NFR-03 | 雙重保存一致性 | 成功畫面出現時，可查到結構化資料、影像 metadata 與可開啟的原始影像；中斷後一般查詢不顯示半成品。 | DBA／測試 |
| NFR-04 | App 私有資料邊界 | 影像、SQLite 與其備份規則均在 App 私有範圍受控；不得在系統相簿、共享儲存或日誌找到原始影像。 | DBA／測試 |
| NFR-05 | 可恢復性 | 模擬寫檔、Room 交易、定稿改名與重啟中斷後，啟動復原可完成、隔離或安全清除 Pending 資產。 | DBA／測試 |
| NFR-06 | 同意可理解性 | 雲端 OCR、AI 文字與 AI 影像三種傳送情境均有不同提示；取消後不得發出請求。 | 設計／測試 |
| NFR-07 | 安全 | APK、原始碼、SQLite、影像路徑、日誌與錯誤回報不含供應商長期 API key 或 ChatGPT 登入憑證。 | 軟體／測試 |
| NFR-08 | 可用性 | 使用者可從空白草稿完成資訊，且任何 Locked 欄位均可編輯、重新分類或重掃；保存期間有可理解的進度與失敗訊息。 | 設計／測試 |

## 7. 角色影響與不在範圍

| 面向 | 判定 | 理由 |
| --- | --- | --- |
| SA | 適用 | 新系統加入即時影像分析、欄位狀態機、影像資產保存、SQLite 與外部服務邊界。 |
| 設計工程師 | 適用 | 對焦提示、候選鎖定、重掃、重分類、保存進度與失敗回復皆為核心互動。 |
| DBA | 適用 | 完成資料需進 App 私有 SQLite，且影像 metadata、狀態、復原及刪除策略需一致。 |
| 系統整合 | 適用 | Android Contacts、雲端 OCR、AI、Gateway 與外部影像來源都是跨系統介面。 |
| 維運 | 有條件適用 | 啟用 Gateway 或付費 AI 時，才需要機密、費用、監控與輪替作業。 |
| 測試 | 適用 | 需驗證即時狀態、雙重保存、重啟復原、本機查詢、同意與故障回復。 |

本版不包含 iOS、桌面程式、Web 查詢網站、多人帳號、同步、分享、任意第三方 AI URL、雲端帳號建立、API 金鑰設定或正式發布。原始影像保存不等於共用、同步或外部傳送。

## 9. 驗收條件摘要

1. 使用者從相機拍攝或選取一張名片，完成後可在本機查詢到結構化欄位及同一筆原始影像。
2. 使用者鎖定後，連續 OCR 結果不得變更該值；再次點選只讓該項重新掃描。
3. 欄位下拉重新分類不得重跑 OCR，且衝突須由使用者選擇處理方式。
4. 在寫檔、資料庫交易或定稿期間強制中斷後，一般查詢不得顯示只有影像或只有欄位的完成記錄；重啟後必須有可驗證的復原結果。
5. 原始影像不得出現在共享圖庫、公開外部儲存、未同意的網路請求或一般日誌中。
6. 離線情境下，拍攝、保存影像、SQLite 入庫與本機查詢均可執行。
