## 1. 背景與目標

使用者希望有一個運行於 Android 手機的應用程式，讓使用者拍攝名片後，將名片文字轉成可編輯的聯絡人資訊。系統必須提供可選的辨識途徑：

1. 離線 OCR：作為預設方式，名片影像與辨識文字留在手機。
2. 雲端 OCR：僅在使用者主動選擇並同意資料傳送後使用。
3. AI 結構化解析：在離線或雲端 OCR 的結果不足時，由使用者主動選擇使用 GPT 或 Gemini 等已核准服務，協助將文字整理為欄位。

本文件記錄的已確認原則是：離線 OCR 預設可用；雲端 OCR 與 AI 只在使用者主動啟用並同意資料傳送後使用。

## 2. 使用者與主要流程

### 2.1 目標使用者

- 持有 Android 手機、需要將紙本名片整理為聯絡人的一般使用者。
- 使用者本人必須對每次上傳名片影像或文字、以及建立聯絡人負責並作出確認。

### 2.2 主要成功流程

1. 使用者拍攝名片，或從裝置選取既有名片影像。
2. App 顯示影像預覽，允許重拍、裁切或放棄。
3. App 以離線 OCR 擷取文字並建立初步欄位草稿。
4. 使用者檢查並手動修正姓名、公司、職稱、電話、電子郵件、網址與地址。
5. 若結果不足，使用者可明確選擇雲端 OCR；系統先顯示將傳送的資料類型、服務提供者與取消選項。
6. 若仍需要，使用者可明確選擇 AI 結構化解析；第一版預設僅傳送 OCR 文字。要傳送名片影像給 AI 時，必須顯示另一層明確同意。
7. 使用者在 App 內確認草稿後，交由 Android 系統聯絡人編輯畫面再次確認並儲存。

系統不得在未經使用者確認的情況下自動新增、覆寫或合併 Android 聯絡人。

## 3. 功能需求

| ID | 需求 |
| --- | --- |
| FR-01 | App 必須支援以手機相機拍攝單張名片，並支援從裝置相簿選取影像。雙面名片是否納入第一版為待決事項。 |
| FR-02 | App 必須在 OCR 前處理影像方向，並讓使用者重拍或裁切；辨識品質不足時須提示重拍，不得把低可信結果當成已確認資料。 |
| FR-03 | App 必須將離線 OCR 設為初始選項。未連網時，離線 OCR 與手動編輯仍須可用。 |
| FR-04 | 雲端 OCR 與 AI 解析均須是使用者主動觸發的選項；每次傳送前必須顯示服務名稱、傳送內容類型、隱私提示與取消選項。 |
| FR-05 | OCR 協調元件必須保留原始辨識文字、文字區塊位置或其他可用證據，供使用者核對欄位來源；未確認的欄位不得隱藏其不確定性。 |
| FR-06 | 欄位解析至少涵蓋姓名、公司、職稱、電話、電子郵件、網站與地址；每一欄可為空，且電話與電子郵件可有多筆。 |
| FR-07 | 使用者必須能在建立聯絡人前編輯、刪除或新增任何欄位。 |
| FR-08 | 第一版應使用 Android 的新增聯絡人 Intent 開啟系統聯絡人編輯器，讓使用者作最後確認；不以直接寫入聯絡人資料庫作為預設實作。 |
| FR-09 | 當雲端服務無網路、逾時、拒絕或回傳無效資料時，App 必須保留本機草稿、顯示原因與可行的本機編輯或重試選項；不得偷偷改送其他服務。 |
| FR-10 | 第一版不保存掃描歷史、名片圖片或雲端帳密；使用者放棄草稿後，暫存資料應清除。若未來需要歷史紀錄，必須另立需求並完成資料庫與保存期限評估。 |

## 4. 辨識模式與資料邊界

| 模式 | 預設狀態 | 可傳送資料 | 預期用途 | 必要互動 |
| --- | --- | --- | --- | --- |
| 離線 OCR | 啟用 | 無 | 讀取中文與拉丁字母名片的基礎文字 | 無網路同意 |
| 雲端 OCR | 停用 | 名片影像或經使用者選擇的影像副本 | 離線結果不足時的文字擷取 | 每次明確同意 |
| AI 文字解析 | 停用 | 預設為 OCR 文字 | 將文字整理為結構化聯絡人欄位 | 每次明確同意 |
| AI 影像解析 | 停用 | 名片影像 | OCR 無法取得足夠文字時的最後選項 | 額外的影像傳送同意 |

第一版的產品流程是由使用者逐步升級辨識方式，而不是由 App 在背景自動上傳或自動切換供應商。

## 5. AI 帳號、Token 與機密管理

### 5.1 已決原則

- ChatGPT 網頁或 App 的登入憑證、Cookie、工作階段 token 都不是此 Android App 可使用的 API 金鑰，App 不得要求、擷取或保存它們。
- ChatGPT 訂閱與 OpenAI API 平台是不同的計費系統；若選用 OpenAI，須由 API 平台的專案與計費機制提供服務能力。
- OpenAI 與 Gemini 的共享服務 API 金鑰不得編譯進 Android APK、放入版本庫或直接由 App 持有。
- 正式產品須透過自有的後端 Proxy / Provider Gateway 保管服務端機密。Android App 只使用本系統簽發的短效 App 工作階段憑證。
- Android Keystore 可用於保護 App 本身的本機加密金鑰或工作階段資料，但不能把嵌入 APK 的供應商 API 金鑰變成可安全公開的憑證。

### 5.2 待決產品政策

- 是否提供「使用者自備 OpenAI 或 Gemini API 金鑰」模式；若提出，必須另做安全、費用告知、遺失撤銷與客服邊界評估，不列入第一版預設。
- 雲端 OCR 與 AI 的實際供應商、資料處理地區、保存政策、費用上限與帳務責任。

## 6. 非功能需求與驗收方向

| ID | 需求／來源 | 驗證方式與通過標準 | 責任 |
| --- | --- | --- | --- |
| NFR-01 | 隱私：已確認的離線優先原則 | 在飛航模式下拍攝、離線 OCR、編輯與開啟聯絡人草稿均可完成；封包測試不得出現未同意的名片資料上傳。 | 測試工程師 |
| NFR-02 | 同意可理解性 | 雲端 OCR、AI 文字與 AI 影像三種傳送情境都顯示不同資料說明；取消後不得送出請求。 | 設計／測試 |
| NFR-03 | 資料正確性 | 使用預先核准的繁體中文與英文名片樣本，人工比對原圖、OCR 文字與欄位草稿；數值門檻待使用者提供可接受標準。 | 測試 |
| NFR-04 | 安全 | APK、原始碼、日誌與錯誤回報均不含 OpenAI、Gemini 或雲端 OCR 的長期服務金鑰。 | 軟體／測試 |
| NFR-05 | 可恢復性 | 雲端請求失敗時，本機草稿可繼續編輯；使用者放棄後才清除暫存。 | 軟體／測試 |
| NFR-06 | 可用性 | 不以 OCR 成功為儲存聯絡人的必要條件；使用者能從空白草稿手動完成資訊。 | 設計／測試 |

目前沒有已確認的回應時間、支援 Android 版本、使用人數、可接受辨識率或成本上限；這些不得在實作前被假定為承諾。

## 8. 明確不在本次第一版範圍

- iOS、桌面程式、Web 管理後台與 CRM / ERP 同步。
- 未經使用者確認的自動儲存、聯絡人合併或批次寫入。
- 名片雲端備份、掃描歷史、多人帳號、登入、分享與匯出。
- 任意使用者輸入的 AI URL 或未知第三方端點。
- 直接在 App 內使用 ChatGPT 登入 token、Cookie 或共用 API 金鑰。
- 雲端供應商帳號建立、金鑰設定、費用承諾或正式部署。
