## 1. 問題、範圍與限制

本系統要把 Android 手機拍攝或選取的名片影像轉成可編輯聯絡人草稿。使用者已確認離線 OCR 優先；任何雲端 OCR 或 AI 服務均須由使用者主動選擇與同意後才可傳送資料。

本次評估只提出可實作的系統邊界、資料流、風險與必要決策。不建立 Android 專案、不安裝套件、不建立雲端帳號、不設定 API 金鑰，也不對外部署。

## 3. 提案架構

### 3.1 推薦結論

採用「離線優先的 Android App + 可選後端 Provider Gateway」架構。App 的核心流程在裝置端完成；只有使用者明確同意後，才經由受控的後端 Gateway 呼叫雲端 OCR 或 AI。Gateway 保管服務端金鑰、套用供應商 allowlist、費用限制、記錄與撤銷策略；APK 不含共享服務 API 金鑰。

名片辨識的主資料流如下：

1. Camera / 相簿輸入進入 App 的影像準備與品質檢查。
2. Offline OCR 執行於裝置端，輸出原始文字與可用的位置資訊。
3. 本機欄位解析器將文字轉成 Contact Draft，並保留可供核對的原始文字。
4. 使用者可直接編輯草稿，或明確選擇 Cloud OCR / AI。
5. Cloud OCR 與 AI 請求僅透過 Gateway；AI 預設傳送 OCR 文字，影像分析需要額外同意。
6. App 最終使用 Android 新增聯絡人 Intent 開啟系統編輯畫面；使用者在系統畫面內儲存。

### 3.2 模組、責任與契約

| 模組／介面 | 職責與資料契約 | 失敗或相容性行為 |
| --- | --- | --- |
| Android UI 與 Consent Controller | 顯示拍攝、模式選擇、資料傳送內容、草稿編輯與確認；保存本次同意狀態。 | 未同意、取消或關閉時不發送網路請求。 |
| Camera / Image Import | 產生臨時影像 URI，處理方向、裁切與重拍。 | 相機權限拒絕時提供相簿選取或手動建立草稿。 |
| Offline OCR Adapter | 封裝裝置端文字辨識；輸入影像，輸出文字區塊與可能的信心資訊。 | OCR 失敗時保留影像預覽、允許重拍或手動輸入，不自動上傳。 |
| Field Parser | 將原始文字整理為姓名、公司、職稱、電話、Email、網址、地址與未分類文字。 | 無法判斷時放入待確認欄位，不丟棄原始文字。 |
| Contact Draft Editor | 讓使用者核對與編輯所有欄位；標示來源和不確定欄位。 | 永遠允許手動完成與放棄。 |
| Provider Gateway | 驗證 App 工作階段、記錄同意用途、路由至允許的雲端 OCR 或 AI 供應商、保管服務端機密與費用控制。 | 逾時、配額或供應商失敗時回傳可理解錯誤；不切換其他供應商。 |
| Cloud OCR Connector | 僅在同意後傳送名片影像，回傳規格化文字結果。 | 僅依使用者指定的供應商與資料類型執行。 |
| AI Structure Connector | 將 OCR 文字或另行同意的影像轉為嚴格欄位資料；回傳欄位、警告與未分類文字。 | 格式錯誤或低可信結果回到人工編輯，不直接建立聯絡人。 |
| Android Contacts Intent | 把已確認草稿交給系統聯絡人編輯器。 | 使用者可在系統畫面取消或修改；App 不宣稱已儲存。 |

### 3.3 信任與資料邊界

| 邊界 | 允許資料 | 禁止事項 |
| --- | --- | --- |
| 裝置內 | 暫存影像、原始 OCR 文字與本次草稿 | 未經選擇的雲端傳送、永久掃描歷史。 |
| App 到 Gateway | 使用者已選擇的資料、短效 App 工作階段憑證、模式與同意記錄。 | OpenAI / Gemini / OCR 服務的長期 API 金鑰、ChatGPT 登入 Cookie 或 token。 |
| Gateway 到供應商 | 僅本次核准的影像或文字、最少必要提示與結構化輸出要求。 | 任意使用者輸入 URL、未核准第三方轉送、未加上供應商限制的請求。 |
| App 到 Contacts Provider | 已確認的欄位草稿。 | 背景直接寫入、未確認覆寫或聯絡人自動合併。 |

## 4. 技術方案與取捨

| 面向 | A：純離線 MVP | B：離線優先 + Gateway（推薦） | C：App 直接內嵌雲端服務 API 金鑰 |
| --- | --- | --- | --- |
| 符合需求 | 只滿足離線 OCR 與手動輸入。 | 滿足離線、可選雲端 OCR 與 GPT / Gemini 結構化需求。 | 表面上可呼叫服務，但不安全。 |
| 隱私與控制 | 最佳；資料不離機。 | 使用者可控，Gateway 可留最小稽核與費用控制。 | 金鑰容易被擷取，名片資料邊界難以控管。 |
| 複雜度 | 最低。 | 中等；需要後端、認證、監控與供應商適配層。 | 初期較低，但安全與帳務風險不可接受。 |
| 擴充與維運 | OCR 成效受本機模型限制。 | 可新增已核准供應商、模型與資料保護規則。 | 不可作為正式產品架構。 |
| 建議 | 可作為第一個可驗證里程碑。 | 對已述產品目標的推薦架構。 | 不採用。 |

離線 OCR 實作建議評估 Android ML Kit 的文字辨識能力。官方文件區分 bundled 與由 Google Play services 動態下載的模型；前者較大但初始化可立即使用，後者較小但首次使用可能需下載。最終模型、語言和最低 Android 版本應以 D-01 與 D-04 的裝置測試決定，不在本草案固定套件版本。

## 5. 安全、帳務與身分設計

- OpenAI 官方安全指引明確指出 API key 不可部署於行動 App，用戶端請求應經自有後端；Gemini 官方指引同樣要求生產環境不要把 key 暴露於行動或 Web 用戶端。
- ChatGPT 訂閱與 OpenAI API 的帳務分開，因此 ChatGPT 登入不等同本產品可使用的 API 授權。
- Gateway 必須以服務端 Secret Manager 或等效機制保存供應商機密，並具備供應商 allowlist、每使用者或每組織用量限制、失敗記錄、輪替與停用程序。
- Android Keystore 只用於保護 App 的本機加密用途或短效工作階段資料；它不是把長期供應商 API key 放進 APK 的替代方案。
- 日誌不得含名片影像、完整 OCR 原文、電子郵件、電話或 API key。若需要診斷，必須使用去識別化事件與可設定的保存期限。

## 6. 故障處理與回復

| 情境 | 使用者可見行為 | 系統處理 |
| --- | --- | --- |
| 相機權限被拒絕 | 說明原因，提供相簿選取與手動輸入。 | 不要求不必要權限。 |
| 影像模糊或 OCR 低品質 | 顯示重拍與人工編輯選項。 | 不自動改送雲端。 |
| 網路不可用 | 雲端選項不可執行，但離線草稿可繼續。 | 保留本機當次草稿。 |
| Gateway / 供應商逾時、配額或拒絕 | 顯示選定服務失敗與重試選項。 | 不自動更換供應商，不丟失本機草稿。 |
| AI 回傳不合格欄位 | 退回 Contact Draft Editor，保留原始 OCR。 | 不新增聯絡人。 |
| 使用者取消聯絡人編輯 | 回到 App 草稿或依使用者選擇放棄。 | 不標示儲存成功。 |

目前沒有資料遷移或回復作業，因第一版沒有 App 資料庫。若未來增加歷史或同步，須先新增資料模型、Migration、備份及刪除策略評估。

## 7. 驗證切入點

| 類別 | 最小驗證工作 | 不可宣稱的範圍 |
| --- | --- | --- |
| 離線 OCR | 以核准樣本在飛航模式下測試繁體中文與英文名片，人工比對欄位。 | 未測試語言或裝置的辨識率。 |
| 同意與網路邊界 | 攔截封包或以測試 Gateway 確認未同意時沒有離機資料。 | 正式隱私或法規認證。 |
| 雲端 / AI | 用測試帳號確認一次明確同意只送指定資料，並處理拒絕與逾時。 | 生產費用、供應商 SLA 或資料處理合規保證。 |
| 聯絡人 | 驗證系統新增聯絡人畫面帶入預期欄位，取消不建立聯絡人。 | 各廠商通訊錄 App 的所有客製行為。 |
| 機密 | 檢查 APK、程式碼與日誌無長期供應商 key。 | 尚未建立後端時的端到端祕密管理。 |

## 8. 決策、風險與下一步

### 8.1 已確認決策

- 離線 OCR 是預設模式。
- 雲端 OCR 和 AI 必須由使用者主動啟用並明確同意資料傳送。
- 聯絡人必須先由使用者檢查與確認。
- 不可把 ChatGPT 登入憑證當成 App API key。

### 8.2 開發前阻擋條件

| 待決問題 | 是否阻擋 | 原因 |
| --- | --- | --- |
| D-01：支援語言 | 是 | 決定離線 OCR 選型與驗收樣本。 |
| D-02：是否保存歷史 | 是 | 決定資料庫、隱私與刪除範圍。 |
| D-03：供應商與 Gateway / 自備金鑰模式 | 是 | 決定身分、機密、費用與後端範圍。 |
| D-04：最低 Android 版本與發佈方式 | 是 | 決定 SDK、相機支援與測試範圍。 |
| D-05：雙面名片與其他擴充功能 | 否，可延後 | 可留為後續 Issue，不影響單面名片 MVP。 |

### 8.3 架構圖

本評估選定的圖示方向是「Unstructured input to structured artifact」語義模式搭配 Architecture 類型，呈現名片影像如何在本機被辨識、在使用者同意下跨越雲端邊界、再成為可編輯聯絡人草稿。

專案尚未設定架構圖的品牌樣式；依圖示規範，第一張自包含 HTML 架構圖必須先取得人類對預設樣式或品牌樣式的選擇。因此本文件暫以可維護的文字與表格記錄架構，不假裝圖示已產出。選擇後，圖示預計存放於 Architecture/diagrams/AR-ISSUE-0001-system-architecture.html。

### 8.4 SA 結論

結論為「有條件採用」。推薦離線優先的 Android App + 可選 Gateway 架構，因其符合使用者的三段式辨識需求，同時避免把服務端 API key 或 ChatGPT 登入憑證暴露在手機端。只有在 D-01 至 D-04 明確決定並完成 UI、整合、維運與測試規劃後，才可進入正式開發。
